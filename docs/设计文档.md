# AI 线上面试中台（InterviewOS）项目设计方案

面向企业招聘场景的 AI 线上面试中台：把组织里的「1 面 → 5 面」标准化为**可编排的面试流程**，用多 Agent 分别承担初面官、追问官、编码考官、记录员、评测员角色，在实时音视频链路上完成 40 到 60 分钟结构化面试，产出**可解释、可复核、可横向对齐**的评估报告，并支持人类面试官实时接管（Copilot 模式）。

技术定位：**Go 高并发实时网关 + 多 Agent 编排引擎 + RAG 知识中台 + 评分一致性校准 + 全链路可观测**。

---

## 0. 先明确一件事：什么才算「大厂企业级」

面试官判断你是不是真做过，看的从来不是「我接了个 GPT」，而是这 6 条：

| 维度 | 玩具项目 | 企业级项目 |
|---|---|---|
| 延迟 | 等 3 到 5 秒出全量回答 | 端到端首字 P95 < 1.5s，支持**打断**（barge-in） |
| 流程 | 一问一答死循环 | **流程可编排**，5 轮面试差异化策略，可断点续跑 |
| 质量 | 直接信 LLM 输出 | **结构化输出 + Schema 校验 + 双模型交叉 + 人工兜底** |
| 一致性 | 同一人两次分数差 30 分 | **Rubric 驱动 + 校准集 + 一致性系数（Kappa）监控** |
| 成本 | 不知道一场多少钱 | **单场面试成本可核算**，按 token/时长拆账，有降级预案 |
| 治理 | 没有 | **多租户隔离、RBAC、审计日志、录音合规、灰度 A/B、SLA** |

**你的核心叙事应该是这一句**：

> AI 不是替代面试官，而是重构面试流水线——把 1 到 2 面这种高重复、可标准化的环节全自动化，把 3 到 5 面变成人机协同，让人类面试官的注意力只花在真正需要判断的地方。

这个叙事很重要，它证明你懂**业务边界**，而不是只会堆技术。

## 1. 五轮面试的产品设计（AI 参与度梯度）

大厂不会让 AI 决定终面。**AI 参与度随轮次递减，人类判断权重递增**，这是全篇最重要的设计决策。

| 轮次 | 名称 | 考察目标 | AI 角色 | AI 参与度 | 人类角色 |
|---|---|---|---|---|---|
| **1 面** | 技术基础面 | 简历真实性、语言/框架基础、项目细节深挖 | 全自动 AI 面试官（数字人 + 语音） | 100% | 无（只做异常复核） |
| **2 面** | 编码 / 算法面 | 现场编码能力、边界思考、复杂度分析 | AI 监考 + AI 判题 + AI 追问 | 90% | 抽检代码质量 |
| **3 面** | 系统设计面 | 架构设计、容量估算、权衡取舍、追问抗压 | AI 主持 + 白板识别 + 抬杠式追问 | 60% | 人类面试官终审 + 主观加权 |
| **4 面** | 领域深度 / 交叉面 | 业务理解、技术选型决策、跨团队协作 | Copilot：实时追问题、实时打分、事实核查 | 30% | 人类主导（AI 辅助） |
| **5 面** | HR / 价值观面 | 动机匹配、稳定性、文化契合、薪酬预期 | AI 初筛行为面 + 纪要生成 | 20% | HR 主导终面决策 |

### 设计要点

**1 面为什么能 100% 自动化？**
因为它的产出是**可验证的事实**（简历里的 ZSet 索引原理、Goroutine 调度、Redis 淘汰策略），不是价值判断。AI 在这里准确率足够高，而且能省掉招聘漏斗最前端 60% 到 70% 的无效面试时间。

**3 面为什么只能 60%？**
系统设计的评分高度依赖面试官的**品味和上下文**（这家公司这个业务的实际约束）。AI 能做的是：主持流程、按 rubric 追问（「如果 QPS 再涨 10 倍呢？」「你怎么保证这个索引不成为瓶颈？」）、把候选人的回答结构化落盘。终审必须是人。

**5 面 AI 只做初筛。**
价值观、薪酬、稳定性涉及法律风险和雇主品牌风险，AI 越界就是事故。这里的 AI 价值在于面试纪要、STAR 结构完整性检查、候选人体验问卷回流。

### 反常识但关键的一点

**留一条「AI 落选 → 人类复议」通道。**
企业级系统必须可申诉。你要有 `candidate_appeal` 表和自动触发人工复盘的机制。这一条写进方案，面试官会立刻认为你想过线上事故。

### 一次面试的完整数据流（按时间轴）

```
T+0      候选人点「开始面试」-> 网关鉴权 -> 编排层加载 interview_plan(第 N 轮)
         -> 从 Redis 读会话快照(断线可恢复) -> 下发音视频权限 + 首题
T+1s     VAD 检测到人声 -> 音频帧(20ms)经 WebSocket 上行
T+1.3s   流式 ASR 出中间结果 -> 前端实时上屏(让候选人感到"在听")
T+8s     语义端点检测判定回答结束 -> 冻结本 turn 文本
T+8.1s   Agent Runtime 走一轮 ReAct
           检索: 从 RAG 拉 JD 能力项 + 简历对应段落 + 相似追问模板
           决策: 给该回答打分 -> 是否追问(深度 <=2) -> 生成下一问
           工具: 需要现场出题时调 question_bank / 代码沙箱
T+8.4s   输出结构化 JSON(评分 + 追问意图 + 话术) -> Schema 校验通过
T+8.5s   流式 TTS 首帧下发 -> 候选人在 1.5s 内听到回应
T+9s     异步: Kafka 投递 turn 事件 -> 落库 + 证据抽取 + 埋点
T+55min  面试结束 -> 触发 Report Job -> 双模型交叉评分 -> 生成评估报告
T+56min  报告推送到面试官工作台 + 候选人状态流转 + 邮件通知

全程: 每一步写 Jaeger span; 音频分片增量上传 OSS; 每 30s 一次 Checkpoint
```

## 3. 核心链路一：实时语音对话（延迟是这个项目的生命线）

### 3.1 延迟预算表（必须背下来，面试高频追问）

| 环节 | 技术方案 | 预算 | 优化手段 |
|---|---|---|---|
| 采集 + 上行 | Opus 编码 20ms 帧 / WebSocket | 60 ms | 就近接入、UDP 优先 |
| VAD 端点判定 | Silero VAD + 能量阈值 | 100 到 300 ms | 静音阈值可配置，动态调整 |
| 流式 ASR 首字 | 云端流式识别 | 150 ms | 长连接预热、技术名词加进热词表 |
| LLM 首 token | 小模型 / 流式输出 | 200 到 400 ms | 首 token 优先、Prompt 瘦身、KV Cache |
| 安全/结构校验 | 本地规则 + Schema | 20 ms | 异步非阻塞校验 |
| TTS 首帧 | 流式合成 | 100 到 200 ms | 音色预加载、文本分句流式推送 |
| 下发 + 播放 | jitter buffer | 50 ms | 自适应缓冲 |
| **合计** | | **约 0.7 到 1.2 s** | **目标 P95 < 1.5s** |

> **面试话术**：我们把延迟拆成 7 段分别做预算管理，每一段都有独立指标和告警，而不是只看端到端。因为端到端变慢时，你要能 5 分钟内定位是哪一段劣化。

这句话直接体现 SLA 意识和排障能力。

### 3.2 打断（Barge-in）——最容易被追问的技术点

候选人打断 AI 说话，是真实面试里必然发生的。难点在于：**用户开始说话时，AI 已经在 TTS 播放，同时 LLM 还在流式生成**。

```go
// 会话上下文树：一次面试 = 一个 root context，每个 turn = 一个子 context
type TurnContext struct {
    ctx        context.Context
    cancel     context.CancelFunc // 用户说话时立即 cancel
    llmStream  Stream             // 流式 LLM 句柄
    ttsStream  Stream             // 流式 TTS 句柄
    playCursor int64              // 已播放到的位置
}

// VAD 检测到人声 -> 触发打断
func (s *Session) onUserSpeechStart() {
    s.currentTurn.cancel()            // 1. 级联取消 LLM/TTS 流
    s.flushClientAudioBuffer()        // 2. 通知客户端清空已缓存音频
    s.turnHistory.markInterrupted()   // 3. 记录"AI 说到一半被打断"
    // 4. 关键: 把 AI 已说出的片段作为"已表达内容"注入下一轮上下文,
    //    避免 AI 重复说同一句话 —— 这是体验分水岭
}
```

**三个必须提到的细节**（说出来就知道你真做过）：

1. **级联取消必须传导到外部服务**：调用 ASR/TTS 厂商 SDK 时要能主动 close stream，否则连接泄漏，几千并发下会打满连接池。
2. **已播音频的截断点要回传**：前端上报 `playedOffset`，后端只把「真正被听到的内容」计入上下文。
3. **打断后不能立刻说话**：要留 200ms 静默，否则 AI 会和候选人抢话。

### 3.3 问答边界：怎么判断「候选人说完了」

三层判定，缺一不可：

1. **能量/VAD 层**：静音超过 800ms（可配）判为疑似结束
2. **语义层**：ASR 结果以「嗯 / 就这些 / 大概这样」结尾，或语法结构完整，提前触发
3. **兜底层**：超过 90s 未结束，AI 温和打断：「要不先聊到这，我想问个延伸问题」

**为什么不能只用 VAD？** 因为候选人思考时的停顿和说完了的停顿，在能量上几乎一样。只用 VAD 会出现「候选人还在想，AI 就抢答了」的灾难体验。

## 4. 核心链路二：面试编排引擎

### 4.1 为什么需要「编排」而不是「循环调用 LLM」

真实面试是有**结构**的：开场破冰 -> 简历深挖 -> 技术深挖 -> 场景题 -> 反问环节。不同轮次结构还不同。硬编码在 Prompt 里会导致不可控、不可观测、不能中途改需求。

所以做**双层编排**。

**第一层：轮次状态机（宏观，确定性）**

```
INIT -> GREETING -> RESUME_DEEP_DIVE -> TECH_FUNDAMENTAL ->
SCENARIO_DESIGN -> CANDIDATE_QA -> WRAP_UP -> SCORING -> REPORT_DONE

每个阶段有: 时长预算 / 最少问题数 / 需要覆盖的能力项集合
例如 RESUME_DEEP_DIVE 必须在 18min 内覆盖 >=4 个项目点
```

状态机是**确定性的 Go 代码**，不是 LLM 决定的。LLM 只在状态内部做决策。

**第二层：问题 DAG（微观，动态）**

```
每个阶段内有若干"能力项"(competency) 需要覆盖, 构成 DAG:

   [简历项目A: 分布式锁]
        |--(追问1) "ZSet 索引为什么能降 RT 70%?"
        |     |--(追问2) "如果 score 冲突怎么办?"
        |--(追问1') "这个方案有什么副作用?"

每个节点携带: 目标能力项 / 参考答案要点 / rubric / 最大追问深度 / 单题时长上限
追问深度 <= 2 (防止把候选人问死), 单题超时自动跳过
```

### 4.2 关键机制：时间与覆盖度的双约束调度

一场面试 45 分钟，但候选人回答长度不可预测。必须有**动态配速**：

```go
type Budget struct {
    TotalMinutes     int               // 45
    StageRemaining   map[Stage]time.Duration
    CompetencyTarget map[string]bool   // 待覆盖能力项
}

// 每次决策前调用: 还剩多少时间 -> 该不该追问 -> 该不该跳过
func (b *Budget) ShouldProbe(remaining time.Duration, importance Level) bool {
    if remaining < 5*time.Minute && importance < High {
        return false
    }
    return true
}
```

**这个设计解决了什么问题？** 没有它的话，AI 会在第一个项目上追问 6 层，聊了 30 分钟，最后系统设计题一个字没问，报告出来发现能力项覆盖度只有 40%，这场面试废了。

> 这是整个项目里**最能体现工程判断力**的一个点，一定要在简历和面试里讲。

### 4.3 Checkpoint 与断线重连

候选人断网、手机没电、浏览器崩溃——真实场景必然发生。

- 每 30s 加每次 turn 结束，会话快照写入 Redis（`interview:session:{sid}` Hash）
- 快照内容：当前状态机阶段 / 已问问题列表 / 当前 turn 上下文摘要 / 剩余时间预算 / 已覆盖能力项 / 音频分片 offset
- 重连时从快照恢复，AI 开场白是：「刚才网络有点波动，我们接着上一个问题——你刚提到 ZSet 索引……」
- 快照 TTL 24h，超时转「面试中断」状态，进入人工处理队列

## 5. 多 Agent 设计（怎么讲得不像是凑数）

**关键**：Agent 拆分必须基于**职责与工具边界**，不能为了显得高级而拆。拆错会被面试官一句话问穿。

```
                    +-------------------------+
                    |   Orchestrator (主控)    |  <- 状态机 + 预算调度
                    | 不是 Agent, 是确定性调度器 |     不参与 LLM 决策
                    +------------+------------+
                                 |
       +---------------+---------+---------+---------------+
       |               |                   |               |
   +--------+     +--------+         +--------+      +--------+
   |面试官   |     |追问     |         |评估     |      |反作弊   |
   |Agent   |     |Agent   |         |Agent   |      |Agent   |
   |提问/话术|     |深挖/抬杠|         |打分/证据|      |异常检测 |
   +----+---+     +----+---+         +----+---+      +----+---+
        |              |                  |               |
        +--------------+---------+--------+---------------+
                                 |
                    +-------------------------+
                    |  Tool Registry (MCP)    |
                    | 题库/简历库/代码沙箱/JD库/日历 |
                    +-------------------------+
```

| Agent | 职责 | 工具 | 输出 | 为什么独立 |
|---|---|---|---|---|
| 面试官 Agent | 生成提问话术、控制口语风格与节奏 | 题库检索、简历检索 | 自然语言问题 | 需要极低延迟，用**小模型 + 流式**，不能背评估的复杂度 |
| 追问 Agent | 基于回答漏洞生成深挖问题 | RAG 检索、参考答案比对 | 追问（最多 2 层） | 需要**更强推理**和更长上下文，用大模型，可容忍 1s 延迟，可异步预生成 |
| 评估 Agent | 逐题打分 + 抽取证据片段 + 生成报告 | Rubric、历史校准数据 | 结构化 JSON | 只在 turn 结束后**异步触发**，不阻塞对话 |
| 反作弊 Agent | 切屏/粘贴/声纹/答题节奏异常 | 浏览器事件、声纹、行为埋点 | 风险分 + 事件链 | 独立进程，**不参与对话链路**，避免拖慢主流程 |

**为什么「面试官」和「追问」要拆成两个 Agent？**

因为它们的延迟要求、模型规模、上下文长度完全不同。面试官 Agent 要 300ms 出话（小模型 + 流式）；追问 Agent 要想清楚候选人的回答哪里有问题（大模型，允许 1.5s）。

如果合并，你只有两个坏选择：全用大模型（延迟崩）或全用小模型（追问质量崩）。

**这个回答是整份方案里含金量最高的一段**，因为它证明你做的是**工程权衡**而不是**架构堆砌**。

## 6. RAG 知识中台（面试的质量上限取决于它）

### 6.1 知识库分层

| 库 | 内容 | 更新频率 | 用途 |
|---|---|---|---|
| JD 能力库 | 岗位 JD 拆解为能力项 + 权重 | 低 | 决定面试提纲与评分权重 |
| 简历库 | 简历结构化实体（项目/技术栈/量化指标） | 每次面试 | 生成个性化深挖问题 |
| 参考答案库 | 每题的**要点集合 + 追问分支 + 常见错误** | 中 | 追问 Agent 的对照基准 |
| 公司技术栈库 | 内部架构、真实业务场景 | 低 | 3 面场景题贴合公司实际 |
| 历史面试库 | 脱敏问答 + 评分 + 最终录用结果 | 持续 | **校准集**，用于评测与 few-shot |

### 6.2 混合检索 + 融合重排（复用你 AI-Ops 项目的方法论）

```
Query(当前问题 + 候选人回答 + 岗位上下文)
   |-- BM25 关键词召回 (精确术语: "ZSet" / "Goroutine" / "幂等")
   |-- 向量召回 (语义: "如何保证缓存一致性")
   |-- 融合: RRF (Reciprocal Rank Fusion)
   |      |-- Rerank 模型重排 -> Top-K
   |             |-- 按需触发: 简单问题跳过检索, 省成本
```

**面试官会问：「为什么不用纯向量检索？」**

答：技术面试里大量是**专有名词的精确匹配**（Goroutine、ZSet、Extism、gRPC 拦截器）。纯向量对这类术语召回不稳定，会出现「问 ZSet，检索到一堆 Redis 通用介绍」。BM25 + RRF 保证术语命中，向量负责覆盖语义泛化。

### 6.3 简历解析：LLM 结构化的经典战场

你在 AI 视频平台已经踩过「LLM JSON 输出不稳」的坑，这里直接复用并升级：

```
PDF/Word 简历 -> 版式解析 -> 文本块
   -> LLM 抽取(结构化)
        |-- JSON Schema 强校验 (字段完整性 / 类型 / 枚举)
        |-- 交叉校验: 时间线连续性 (2024.06 到 2025.03 不能倒挂)
        |-- 一致性校验: 技能列表 与 项目描述中出现的技能 取交集
        |-- 失败 -> 自动重试(带错误信息回灌) -> 连续 2 次失败 -> 人工标注队列
```

**必须配套的产出**：结构化结果落成 `resume_entity` 表并保留**原文 offset**。这样追问时能定位「简历第 3 段说他用了 ZSet，问他为什么选 ZSet 而不是 Hash」。

能引用原文坐标的追问，才叫「读过简历的面试官」。

## 7. 评分体系与一致性（最容易被低估、最容易拉开差距）

### 7.1 Rubric 驱动，而不是让 LLM 自由发挥打个分

```
能力项: 分布式系统设计 (权重 30%)
  L1 未掌握: 无法描述基本概念
  L2 了解:   知道概念, 无法落地
  L3 熟练:   能设计并说明权衡
  L4 精通:   能预判瓶颈, 给出容量估算与降级方案
  L5 专家:   有跨系统权衡经验, 能提出我们没想到的方案

每个等级绑定:
  - 判定要点 (必须命中的关键词/概念)
  - 反例 (出现"所有数据放 Redis 就行" -> 直接 L1,
          不允许因为表达流畅而加分)
```

### 7.2 抗幻觉四件套

1. **证据绑定（Evidence Binding）**：每个分数必须挂 1 到 3 条**候选人原话片段 + 时间戳**。没有证据的分数直接作废。这是防幻觉最有效的手段。
2. **双模型交叉评分**：主模型 + 独立模型分别打分，分歧超过 1 级触发仲裁（第三次打分或人工复核）。
3. **校准集回归**：维护 200 场以上已有人工评分的脱敏面试作为 golden set。**每次改 Prompt 或换模型，先跑回归**，看 Kappa 系数和 MAE。
4. **分数分布监控**：线上实时看每个 AI 面试官的分数分布。如果突然 80% 都给 L4，说明 Prompt 漂移了，自动告警。

### 7.3 一致性指标（说得出数字，档次立刻不同）

| 指标 | 含义 | 目标 |
|---|---|---|
| 与人工评分一致性（Weighted Kappa） | 同意程度 | > 0.7 可用 |
| MAE | 平均绝对误差 | < 0.5 级 |
| 重测稳定性 | 同一录音两次评分差异 | 差异不超过 1 级占比 > 95% |
| 人际一致率 | 双模型同分比例 | > 85% |
| 通过率偏差 | AI 通过率 vs 人类通过率 | 偏差 < 8% |

> 「通过率偏差 < 8%」这个指标杀伤力极大——它说明你考虑的是**业务影响**，而不只是模型指标。AI 面试官偏严会漏掉优秀候选人（造成招聘损失）；偏松，会让 HR 面被无效简历淹掉。

**面试域（核心）**

```

   +-- interview_round  单轮配置(考察能力项/时长/是否有编程题/AI 权限)
interview_session     一场面试会话
   |-- session_snapshot  Checkpoint 快照(Redis 主存, MySQL 归档)
   |-- qa_turn           每轮问答(问题/ASR 文本/音频 OSS 路径/耗时/token)
   |-- evidence          证据片段(候选人原话 + 时间戳 + 对应能力项)
   |                     <- 评分可解释性的基石, 也是复盘材料
   |-- evaluation_dim    维度评分(能力项 x 等级 x 理由 x 证据引用)
   |-- coding_submission 编程题提交 + 判题结果 + 过程快照
   |-- anti_cheat_event  反作弊事件(切屏/粘贴/多人声纹/异常节奏)
   +-- report            最终报告(结构化 + 可读文本 + 录制回放)
```

**AI 治理域**

```
model_call_log    LLM/ASR/TTS 调用明细(模型/入出 token/耗时/成本/租户)
prompt_version    Prompt 版本管理 + A/B 实验分组
eval_run          模型评测运行记录(校准集回归结果)
human_review      人工复核记录(争议分的仲裁过程)
```

### 8.2 存储选型理由（每一句都要能回答「为什么」）

| 存储 | 用途 | 选型理由 |
|---|---|---|
| **MySQL** | 业务主数据 | 事务强一致（面试状态流转不能乱）；按 `tenant_id + candidate_id` 分库分表；`qa_turn` 按 `session_id` 分表并冷热分离 |
| **Redis** | 会话状态 / 快照 / 分布式锁 / 限流 / 热点缓存 | 面试是长事务，状态必须常驻内存；Cluster 分片 + Lua 保证原子性 |
| **Kafka** | 事件总线（turn 事件、评分任务、埋点、审计） | 削峰：秋招峰值几千路并发，评分和报告生成必须异步；也做审计日志的不可变流 |
| **Elasticsearch** | 题库检索 / 面试记录全文检索 / 日志 | 面试官要能按「候选人提到过 Kafka 幂等」搜历史记录 |
| **OSS** | 音视频录制、简历文件 | 冷数据，对象存储最经济；分级存储（30 天热转归档） |
| **Airflow** | 离线 ETL（校准集回归、题库挖掘、日报） | 批处理 DAG，与你已有的 Airflow 经验直接复用 |

### 8.3 一个必须讲的细节：`qa_turn` 的数据量级

```
一场面试 45 分钟 约 25 到 40 个 turn
每 turn 存: ASR 文本 + 音频分片元数据 + Agent 完整 trace + 耗时
单 turn 约 15 KB (不含音频) -> 单场约 500 KB 元数据 + 200 MB 音频

秋招峰值: 10 万场面试/天
  -> 元数据 50 GB/天 -> 按月分区, 3 个月后归档
  -> 音频 20 TB/天  <- 这个数字必须提前算, 否则第一个月就撑爆
```

**能主动说出「音频存储成本会被低估」的人，面试官会认定你做过容量规划。**

对应措施：录制可配置开关（部分企业出于合规要求不录制）、Opus 压缩、分级存储、过期自动清理、按租户配额。

## 9. 企业级治理（这块决定你是「开发者」还是「工程师」）

### 9.1 多租户隔离

每张业务表带 `tenant_id`；Redis key 前缀隔离；ES 按 tenant 分索引；LLM 调用按租户配额限流（防一个客户打爆全局）。

### 9.2 限流与降级（面试现场不能挂）

```
三级降级:
L0 正常:     全流式 ASR + LLM + 流式 TTS
L1 TTS 降级: TTS 供应商不可用 -> 切备用供应商 -> 再不可用切"文本 + 提示音"
L2 LLM 降级: 大模型超时 -> 切小模型 -> 再超时 -> 抛出"面试官稍后回电", 转人工
L3 全局降级: 关闭反作弊实时检测、关闭数字人视频, 保语音对话主干

原则: 面试的"对话可用性" > "画质" > "附加功能"
```

### 9.3 成本核算（面试官几乎必问）

```
单场 45 分钟面试成本 约等于:
  ASR: 45min x 单价
  LLM: 25 turn x (输入 4K + 输出 300 token) x 单价 x 2(追问 + 评分)
  TTS: 25 turn x 150 字
  音视频 / 存储 / 带宽

关键优化:
  1. Prompt 前缀固定 -> KV Cache 命中, 输入成本可降 50% 以上
  2. 简单轮次跳过大模型(分级路由): 破冰/寒暄用小模型
  3. 评分 Agent 用批处理(同一场所有 turn 一次提交), 而非逐 turn 调用
  4. 答案缓存: 结构高度相似的问题(如自我介绍类)结果可复用
```

### 9.4 合规（在中国做招聘系统绕不开）

- **个保法**：简历和录音属于个人信息，需候选人**明示同意**（开始面试前弹窗 + 记录同意快照与时间戳）
- **留存策略**：录音默认留存 6 个月，可配置；到期自动删除并留删除审计
- **AI 披露义务**：必须明确告知「本轮由 AI 面试官主持」，**不得伪装成真人**
- **反作弊的边界**：可以做切屏、粘贴、声纹检测；**摄像头行为分析要谨慎**，不要做情绪识别和面相分析，这是明确的高风险禁区
- **算法歧视防控**：评分模型不得使用与岗位无关的特征（性别、年龄、地域、院校层次只能用于合规统计，不能进评分）

> 「不做情绪识别和面相分析」这句话在面试里说出来，会让人立刻觉得你**有技术伦理判断力**。

### 9.5 可观测性（你已经很熟，直接复用）

| 层 | 指标 |
|---|---|
| 接入层 | 在线连接数、建连成功率、消息延迟 P99、心跳超时率 |
| 对话链路 | **首字延迟 P95**、打断成功率、ASR 字准率、TTS 首帧延迟 |
| Agent | 单 turn 决策耗时、工具调用成功率、Schema 校验通过率、重试率 |
| 质量 | 评分分布、双模型分歧率、人工复核推翻率 |
| 成本 | 单场成本、token/分钟、各租户消耗 TOP |
| 业务 | 面试完成率、中断率、候选人满意度 CSAT、面试官采纳率 |

**Jaeger 链路追踪特别重要**：一次面试跨越网关、ASR、Agent、LLM、TTS 五个系统，没有 trace 根本没法排查「为什么这轮 3.5 秒才回话」。

Trace 要带 `session_id / turn_id / tenant_id` 作为 baggage，从网关一路透传到底。

## 13. 面试官高频追问与标准答案

### Q1：为什么面试系统要用 Go，而不是 Python 或 Java？

> 面试链路是 IO 密集型长连接场景：单机要扛大量 WebSocket 连接，每场面试有 ASR 流、TTS 流、LLM 流多条并发长连接。Go 的 goroutine 让单机连接数比线程模型高 1 到 2 个数量级，内存占用也更低。而且我们大量调用外部 AI 服务，Go 的 context 级联取消天然适合**打断**这种需要穿透多层取消的场景——这是我在 IM 项目里处理连接回收时验证过的。

### Q2：你怎么保证 AI 评分是公平的？

> 分四层：一是题库和 rubric 由人工预先定义并通过评审，AI 不自由发挥；二是每个分数必须绑定候选人原话证据，无证据的分数作废；三是双模型交叉，分歧超过一级触发第三次仲裁或人工复核；四是线上监控分数分布，发现分数漂移就告警并回滚 Prompt。另外必须有候选人复议通道。

### Q3：如果 LLM 输出格式错了怎么办？

> 我在 AI 视频生成项目里踩过这个坑：LLM 输出 JSON 不稳定，格式一错就污染下游数据。这里的处理是 Schema 强校验加字段完整性、枚举校验，再加业务交叉校验（比如评分等级必须在 L1 到 L5、证据必须能匹配到某条 `qa_turn`）。失败自动重试并把错误信息回灌给模型，连续两次失败降级到规则兜底或转人工。这套方案在实际场景里把脏数据率从 ___ 降到 ___。

### Q4：45 分钟的面试上下文会超长，怎么处理？

> 分层记忆。短期用滑动窗口保留最近 3 到 5 轮完整对话，保证连贯性；中期对更早轮次做摘要压缩，但**评分相关的证据片段结构化抽出来单独存**，不参与摘要，因为摘要会丢细节；长期记忆存 MySQL，按需检索。另外面试官 Agent 只需要当前问题加最近上下文，而评估 Agent 是批处理整场，两者上下文策略不同——这也是拆 Agent 的原因之一。

### Q5：怎么防替考和作弊？

> 分软硬件两侧。软件侧：切屏检测、粘贴检测、答题节奏异常、同一设备多场面试。硬件侧：声纹比对、异常音画检测。但我有明确边界——**不做情绪识别和面相分析**，那既不可靠也涉及算法歧视风险。而且反作弊的产出是**风险分加事件链**，供人工判断，不是自动淘汰。

### Q6：几千路并发面试，瓶颈在哪？

> 三个瓶颈，按顺序：一是**长连接网关**，连接数和消息吞吐，用连接分片加多实例水平扩展；二是**外部 AI 服务配额**，ASR/TTS/LLM 通常是 SaaS，有并发配额，必须有连接池、预热、多供应商路由和降级；三是**录音存储**，最容易被低估，10 万场一天会产生几十 TB 音频，必须做分级存储和留存策略。计算本身（Go 服务）反而是最不瓶颈的。

### Q7：为什么不用现成的开源数字人方案？自己做编排有什么价值？

> 数字人只解决「表现得像个人」，不解决「面试要考察什么、怎么追问、怎么评分」。开源方案是**表现层**，而面试的护城河在**编排与评测**：能力项覆盖度、追问策略、评分一致性、可解释证据。我们完全可以接开源数字人做表现层，把编排引擎作为自己的核心资产。

### Q8：候选人回答完全跑题，AI 怎么处理？

> 追问 Agent 有一步「跑题检测」：把回答与当前能力项的判定要点做语义比对，低于阈值判定跑题。处理策略按阶段不同——初面温和拉回（「这块我们后面再聊，我想先确认下刚才那个问题」），3 面场景题允许一定发散但记入「沟通聚焦度」维度。跑题本身也是评分信号，会记录但不会单次否决。

### Q9：你怎么衡量这个系统「有用」？

> 业务指标：每轮面试平均耗时下降、HR 初筛到 1 面的周期缩短、面试官人均可面试场次提升。质量指标：AI 通过率与人类通过率的偏差、AI 面试通过者进入后续轮次的通过率（如果 AI 筛掉的人在别的渠道表现很好，说明筛错了）。体验指标：候选人完成率、CSAT。技术指标：首字延迟、中断率、单场成本。

### Q10：这个项目最大的技术风险是什么？

> 我认为是**评分一致性**。延迟、并发都是工程问题，有明确解法；但「AI 给 70 分、人类面试官给 50 分」这种分歧，会直接摧毁招聘团队对系统的信任。所以我把校准集和一致性监控放在很靠前的位置——每次改 Prompt 或换模型先跑回归，Kappa 掉了就不许上线。**这个项目里，可解释性和一致性比模型效果更重要。**

## 14. 讲这个项目时要避开的坑

| 别说 | 改成 |
|---|---|
| 「用 AI 自动决定候选人录不录用」 | 「AI 输出结构化评估与证据，录用决策始终由人做」 |
| 「用了 GPT-4，效果很好」 | 「按延迟和上下文需求做了分级模型路由」 |
| 「多 Agent 协同，很智能」 | 「三个 Agent 的延迟、模型、上下文需求不同，所以拆分」 |
| 「延迟 500ms」 | 「首字延迟 P95 1.2s，分 7 段预算管理，最慢段是 VAD 端点判定」 |
| 「评分准确率 95%」 | 「与人工评分 Weighted Kappa 0.72，通过率偏差 6%」 |
| 「支持 10 万并发」（没测过） | 「单机压测到 X 千连接，水平扩展方案是 Y，瓶颈在 Z」 |

**最后一条原则**：凡是你说出口的数字，都要能被追问三层。**没测过的数字一律说「设计目标是 X，我实测的是 Y」**——面试官对有边界感的候选人评价远高于能吹的候选人。

## 附录 B：能力项覆盖度索引设计（复用你的 ZSet 经验）

```go
// 用 Redis ZSet 维护"本场面试还需覆盖的能力项"及其权重与紧迫度
// key: interview:cover:{session_id}
// member: competency_id   score: 权重 x 紧迫度

func (e *Engine) NextCompetency(sid string) (string, error) {
    // ZREVRANGE 取当前最该问的能力项
    // 每问过一个: ZREM 并记录已覆盖
    // 时间紧迫时, 用 ZRANGEBYSCORE 只取高权重项, 放弃低权重
    return e.redis.ZRevRange(ctx, "interview:cover:"+sid, 0, 0).Result()
}
```

**这个设计的价值**：把「这场面试还剩哪些没考」从一次全表扫描变成一个 O(log N) 的 ZSet 操作，跟你在 IM 项目里用 ZSet 索引降 RT 的思路完全一致——**这正好是简历能力延续的证据**。
